## What works

- `/workspace`: Thura-branded six-app preview, preserving the prototype's layout, browser-local state, themes, Contacts-to-Chat and Calendar-to-Meet interactions. A persistent banner describes its simulated behavior. Its storage namespace is `thura:demo:v1:`; it never contains live account data or credentials.
- `/app`: authenticated workspace shell with persistent Mail, Contacts, Drive, Calendar, Matrix Chat, and LiveKit Meet. Mail includes server-backed autosaved drafts, recipients, private attachments, signed raw-MIME ingress, server-side folder search and cursor paging, read/star/folder actions, reply/forward with retained attachments, shared-contact recipient suggestions, scheduled delivery and undo, server-sanitized sandboxed formatted reading, and opt-in private CID thumbnails. Outbound connectors use each mailbox’s operator-controlled credentials. See [mail connectors](mail-connectors.md).
- Drive: folders, private resumable uploads, SHA-256 verification, immutable versions, conflict detection, downloads, trash/restore, administrator permanent deletion, private background PNG/text previews, workspace quotas, transactional object cleanup, and expiring/revocable read-only anonymous or email-restricted links. See [Drive limits and sharing](drive.md).
- Office editing: optional ONLYOFFICE 9.0.4 connector, signed configurations/source tickets, authenticated callbacks, immutable saved versions, conflict refusal, and current membership checks. Real DOCX and XLSX fixtures have been edited, saved, and downloaded through the connector. See [office configuration and limits](office.md).
- Calendar: shared/personal access, day/week/month/agenda views, timezone-aware events, bounded recurrence, per-occurrence exceptions, sequence checks, cancellation, atomic UID-scoped ICS import/export, explicit invitations/cancellations, bounded guest RSVP grants, validated ICS replies, and personal email reminders. See [Calendar behavior and limits](calendar.md).
- Chat: real Matrix application-service channels, private conversations, current-membership API authorization, replies, read markers, retained history, anchored backfill, bounded reconnect bridging, Drive-file copies, and explicit admin-controlled external invitations/bans. Two-domain Synapse tests verify bidirectional messages, attachment bytes, send deduplication, and bans. Rooms are explicitly server-readable. See [Chat configuration and limits](chat.md).
- Meet: current-member access, workspace-bound scoped LiveKit tokens, verified/idempotent webhooks, session-aware leaves, creator/admin room ending, camera/microphone/screen controls, and membership reconciliation. Guest access, recording and transcription are disabled. See [meeting configuration and acceptance limits](meet.md).
- `/contacts`: real sign-in, workspace selection, shared contacts with create/edit/delete/search/favorites, persisted through typed Go APIs to Postgres. All frontend API requests use the generated Līdza client. Signing out clears the client query cache.
- Public registration and external identity providers are disabled. Operators provision initial owners; workspace administrators invite members by email. Password sign-in is the release choice recorded in the completed brief.
- Workspace membership is read from `auth_member` for every request. Recognized owner/admin/member roles all read and edit workspace contacts. Unknown roles and app-wide scopes grant no workspace access. Contact mutation queries include both workspace and contact IDs.
- `/members`: roster, invitations, revocation, role changes, and member removal. Owners manage all roles; admins invite/remove ordinary members. Workspace locking protects the last owner, including simultaneous removals. Owners/admins can page/filter durable workspace activity; successful access/sharing changes audit in the business transaction, and required audit failures roll back the change.
- `/invite`: one-time invitation acceptance for new or existing accounts. Tokens are hashed, expire in 72 hours, and are delivered through the official mail/jobs packs. New account creation, verified-email marking, membership, and acceptance commit atomically. Existing accounts must sign in as the invited email. Old invitations cannot change an existing member's role; removing the inviter's authority invalidates their outstanding invitations.
- `/forgot`, `/reset`, `/verify`: frontend account recovery and verification flows backed by Līdza authentication.
- The operator can create a workspace with an existing account as its owner. Workspace and owner membership are inserted in one transaction.

## Run and provision

Run `lidza install`, then `lidza dev`. Open `/workspace` for the sample or `/contacts` for real contacts. The cloud environment uses `/workspace/.lidza-tools/env` for its toolchain and `/workspace/.lidza-tools/start-services.sh` for Postgres and Valkey.

Use the application's local `lidza mcp` tools for initial operator provisioning:

1. `app_provision_account`: `email`, `name`, and a strong `password` (at least 12 characters; Līdza's password policy also applies). Supply the password privately, never in committed files or saved command examples. This creates an account without opening a session or sending an email.
2. `app_create_workspace`: `name` and `ownerEmail` of that account. This grants the owner role. Repeating this operation creates another workspace; it is not an idempotent upsert.
3. Sign in at `/contacts` with that account.

These tools carry operator authority and have no public HTTP API route. Keep any `LIDZA_MCP_TOKEN` private; remote MCP access, if explicitly enabled, has the same operator authority. No production account has been provisioned by this implementation.

## SMIP sender recovery reference

The isolated SMIP/0.1 reference now includes a durable Unix sender outbox. It saves the signed packet and uncertain attempt marker before network contact, persists verified receipts, reconciles lost acknowledgements with the unchanged packet after restart, and separates definitely unsent expiry from uncertain or blocked attempts. Automatic retry uses bounded jittered backoff; permanent errors require explicit resume. The retained queue and due-page sizes are bounded. No Thura route, provider or job is enabled by this reference; application adapters still need transactional authorization/import and storage-pack integration. See [the protocol contract](protocols/smip-v0.1.md) for state semantics and operational limits.

## Opt-in SMIP receive, review and file import

The experimental track now includes an app-hosted receive endpoint, durable Postgres packets/receipts, administrator-created workspace bindings and a Chat review panel that appears only when enabled by the operator. Pairing authenticates servers; bindings authorize one exact sender/recipient/stream for the whole local workspace. No remote signature creates membership. Disabling a binding prevents new admissions while preserving already accepted receipts. Inbox retention is capped at 1,000 records / 64 MiB decoded content per workspace; paged views exclude file payloads and public/private signing configuration.

Files remain accepted transfers until a current member explicitly imports them. Import verifies the signed bytes again, checks folder, retained/reserved Drive quota and file-count limits, and commits one immutable version and its import marker together. Concurrent imports converge; failed storage/audit writes roll back metadata. Orphan objects use ordinary reference-aware Drive sweeping after its grace period. The adapter accepts at most 10 MiB files to match Drive, keeps them as opaque downloads, and does not claim malware scanning or encrypted storage. See [deployment and API details](protocols/smip-thura.md). The subsequent sender integration below completes the paired-server transport path; Matrix conversations are unchanged.

## SMIP app sender and job recovery

The opt-in transport now sends chat and immutable current Drive snapshots through member-authorized app APIs and durable jobs. Operator origins and peer/local historical keys stay sealed and frozen at startup. Queue writes and their jobs commit together; workers recheck the originating member and enabled binding, commit uncertainty before network contact, and record acceptance only after verifying and durably storing a bound signed receipt. Reconciliation retries the original packet with bounded jitter and a 32-attempt budget. Permanent errors pause for explicit owner/admin resume; an expired unattempted packet stays unsent. Retained outbox and review pages are bounded independently of the inbox.

The Chat review panel provides peer-stream selection, text/file queueing and honest delivery status. Failed queue responses retain their original transaction ID for retry; acceptance does not imply reading or file import. Local source edits/trash do not alter a queued copy. Tests exercise lost acknowledgements after expiry, original signed-byte preservation, membership/consent withdrawal, permanent-error resume, concurrent dispatch, real durable-worker delivery and exact end-to-end binary import. Public deployment, E2EE, discovery, ordered/reply/group events, malware scanning and cross-protocol bridging remain outside this experimental transport.

The complete 47-test browser suite passes with one worker, including inert SMIP text/file review, failed import recovery, authorization-error hiding and lost queue-response retry under the same ID. App sender race checks pass, including two domain-scoped real worker processes delivering in both directions, local receipt-commit failure and unsent expiry. The protocol race suite and independent Node vectors preserve the original wire signatures. Deployment-specific peer configuration/TLS remains an operator action.
