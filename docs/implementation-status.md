# Implementation status

The uploaded `Orbit_Workspace_React (1).zip` now runs inside the published Līdza application. Its source was inspected and imported into `src/workspace`; its built assets, dependency lockfile, standalone server, and setup instructions were not adopted. No Rails runtime or local Līdza checkout is used.

## What works

- `/workspace`: Thura-branded six-app preview, preserving the prototype's layout, browser-local state, themes, Contacts-to-Chat and Calendar-to-Meet interactions. A persistent banner describes its simulated behavior. Its storage namespace is `thura:demo:v1:`; it never contains live account data or credentials.
- `/app`: authenticated workspace shell with persistent Mail, Contacts, Drive, Calendar, Matrix Chat, and LiveKit Meet. Mail includes server-backed autosaved drafts, recipients, private attachments, signed raw-MIME ingress, server-side folder search and cursor paging, read/star/folder actions, reply/forward, scheduled delivery and undo. Outbound connectors use each mailbox’s operator-controlled credentials. See [mail connectors](mail-connectors.md).
- Drive: folders, private resumable uploads, SHA-256 verification, immutable versions, conflict detection, downloads, trash/restore, administrator permanent deletion, workspace quotas, transactional object cleanup, and expiring/revocable read-only anonymous or email-restricted links. See [Drive limits and sharing](drive.md).
- Office editing: optional ONLYOFFICE 9.0.4 connector, signed configurations/source tickets, authenticated callbacks, immutable saved versions, conflict refusal, and current membership checks. Real DOCX and XLSX fixtures have been edited, saved, and downloaded through the connector. See [office configuration and limits](office.md).
- Calendar: shared/personal access, day/week/month/agenda views, timezone-aware events, bounded recurrence, per-occurrence exceptions, sequence checks, cancellation, atomic UID-scoped ICS import/export, explicit invitations/cancellations, bounded guest RSVP grants, validated ICS replies, and personal email reminders. See [Calendar behavior and limits](calendar.md).
- Chat: real Matrix application-service channels, private conversations, current-membership API authorization, replies, read markers, paginated backfill/polling, Drive-file copies, and explicit admin-controlled external invitations/bans. Two-domain Synapse tests verify bidirectional messages, attachment bytes, send deduplication, and bans. Rooms are explicitly server-readable. See [Chat configuration and limits](chat.md).
- Meet: current-member access, workspace-bound scoped LiveKit tokens, verified/idempotent webhooks, session-aware leaves, creator/admin room ending, camera/microphone/screen controls, and membership reconciliation. Guest access, recording and transcription are disabled. See [meeting configuration and acceptance limits](meet.md).
- `/contacts`: real sign-in, workspace selection, shared contacts with create/edit/delete/search/favorites, persisted through typed Go APIs to Postgres. All frontend API requests use the generated Līdza client. Signing out clears the client query cache.
- Public registration and external identity providers are disabled. Operators provision initial owners; workspace administrators invite members by email. Password sign-in is a provisional starting point while the sign-in brief question remains open.
- Workspace membership is read from `auth_member` for every request. Recognized owner/admin/member roles all read and edit workspace contacts. Unknown roles and app-wide scopes grant no workspace access. Contact mutation queries include both workspace and contact IDs.
- `/members`: roster, invitations, revocation, role changes, and member removal. Owners manage all roles; admins invite/remove ordinary members. Workspace locking protects the last owner, including simultaneous removals.
- `/invite`: one-time invitation acceptance for new or existing accounts. Tokens are hashed, expire in 72 hours, and are delivered through the official mail/jobs packs. New account creation, verified-email marking, membership, and acceptance commit atomically. Existing accounts must sign in as the invited email. Old invitations cannot change an existing member's role; removing the inviter's authority invalidates their outstanding invitations.
- `/forgot`, `/reset`, `/verify`: frontend account recovery and verification flows backed by Līdza authentication.
- The operator can create a workspace with an existing account as its owner. Workspace and owner membership are inserted in one transaction.

## Run and provision

Run `lidza install`, then `lidza dev`. Open `/workspace` for the sample or `/contacts` for real contacts. The cloud environment uses `/workspace/.lidza-tools/env` for its toolchain and `/workspace/.lidza-tools/start-services.sh` for Postgres and Valkey.

Use the application's local `lidza mcp` tools for initial operator provisioning:

1. `app_provision_account`: `email`, `name`, and a strong `password` (at least 12 characters; Līdza's password policy also applies). Supply the password privately, never in committed files or saved command examples. This creates an account without opening a session or sending an email.
2. `app_create_workspace`: `name` and `ownerEmail` of that account. This grants the owner role. Repeating this operation creates another workspace; it is not an idempotent upsert.
3. Sign in at `/contacts` with that account.

These tools carry operator authority and have no public HTTP API route. Keep any `LIDZA_MCP_TOKEN` private; remote MCP access, if explicitly enabled, has the same operator authority. No production account has been provisioned by this implementation.

## First-version release completion

The deployment default is Debian Postfix, selected by the developer; every operator chooses their hosts and domains. The supplied adapter preserves the distribution's standard services, rejects unknown recipients/open relay, signs bounded raw-MIME ingestion, and retains delivery on temporary failure. A real Postfix 3.10.13 fixture proved inbound bytes, deduplication after a lost acknowledgment, deferred delivery while Thura was stopped, queue survival across MTA restart, and outbound delivery through the official Līdza SMTP pack to an isolated local sink. No internet recipients or production credentials were used. See [Postfix deployment](postfix.md).

Draft edits autosave after a 750 ms pause. Writes serialize; a send drains the latest snapshot. Failed saves stay visibly unsaved and can be retried. Browser close/reload warns while dirty; internal unmount attempts a final flush. Waiting for “Draft saved” is the persistence acknowledgment, and concurrent editors remain last-write-wins. Mail/Contacts fetch bounded cursor pages (defaults 50/100, maximum 200) and search the full folder/directory. A Go integration test traversed 603 contacts and 251 messages without duplicate/missing ties and checked literal search, limits, malformed cursors, mailbox substitution and revoked membership. The browser suite additionally exercises next-page controls against real small server pages.

The landing/About pages now provide product entry points instead of starter implementation instructions. Remaining recording/transcription, SMIP, additional hosted ingress adapters and unconfirmed expanded contact fields are later scope. Each deployment must still configure its own credentials, DNS/TLS/storage/provider endpoints and perform internet-delivery and physical-device/TURN acceptance; local fixtures do not establish those deployment-specific results. No production deployment or credential setup was performed on a user's behalf.

Final transport acceptance also proves a full 10 MiB uploaded attachment through Līdza → Postfix → the local SMTP sink with identical decoded bytes. Loopback submission advertises 16 MiB to accommodate MIME/base64 overhead; the separate inbound listener and existing raw API retain 12 MiB. Implicit plus-address expansion is disabled, and an unmapped plus address is refused at SMTP. Restart tests exercise both listener definitions and their limits. The final production-page audit measured every one of the 12 routes in isolated browser processes and passed default size/CLS budgets, with zero measured layout shift (Home initial JavaScript 113,782 bytes, About zero).
